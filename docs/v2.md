# AXEL v2 program (`axel_v2`)

`axel_v2` is the second version of the AXEL on-chain program: one Anchor program that runs the whole life of a tokenized taxi car. It takes the raise in escrow, keeps a KYC registry, runs the share mint's transfer hook, distributes attested fleet revenue and records telemetry. It also lets a holder who lost its key get its shares back.

- Program ID: `AXLcoEH3vJXUSL7nEr1T4d77NarThcbVrnbBzBR8XPZi` (not deployed yet; the keypair is kept outside the repository).
- Source: [`programs/axel-v2`](../programs/axel-v2). What the admin can and cannot do: [`programs/axel-v2/README.md`](../programs/axel-v2/README.md).
- Tests: [`tests-v2/`](../tests-v2) (LiteSVM) and `cargo test -p axel-v2`.
- IDL for the frontend: [`frontend/src/lib/solana/idl-v2/`](../frontend/src/lib/solana/idl-v2). TypeScript client: [`sdk/axel-v2/`](../sdk/axel-v2).
- v1 (`programs/axel`, `programs/transfer-hook`) stays in the repository as legacy. Its limitations and the v2 fix for each are listed in [v1 limitation → v2 fix](#v1-limitation--v2-fix).

## Architecture

```
                       admin (Squads on mainnet)
            create / activate / cancel / pause / close / propose recovery
                                   │
 KYC authority (backend) ──► Investor records      oracle (fleet reporting system)
 demo KYC key (devnet)             │                 │ telemetry, co-signs deposits
                                   ▼                 ▼
 investor ──buy_shares──► escrow vault ──activate──► operator ATA (raise − fee)
    ▲                          │  └───────────────► treasury ATA (raise fee)
    │ refund (Failed)          │
    └──────────────────────────┘
 operator ──deposit_revenue (+ oracle signature)──► revenue vault ──claim──► holder's own ATA
                                        └─────────► treasury ATA (revenue fee)

 shares: mint_to (buy_shares) · burn (refund, close_position after Closed)
         burn + mint of the same amount (execute_recovery) · holder transfers through the hook
```

Roles:

| Role | Key | Can |
| :--- | :--- | :--- |
| Upgrade authority | deployer, Squads on mainnet | upgrade the program; call `initialize_config` once |
| Admin | `Config.admin`, Squads on mainnet | create projects, activate or cancel a raise, pause, resume and close projects, change operator and oracle, update the config within hard caps, propose a recovery |
| KYC authority | `Config.kyc_authority`, the backend's Sumsub key | write any KYC record |
| Demo KYC authority | `Config.demo_kyc_authority`, devnet only (default key disables it) | grant or revoke DEMO access for at most 30 days; never a sanctions freeze |
| Operator | `Project.operator`, the fleet | receive the raise on activation; deposit revenue |
| Oracle | `Project.oracle`, the fleet's reporting system | record telemetry; co-sign every revenue deposit |
| Anyone | any wallet | finalize a raise, open a position for a verified wallet, claim for a holder, execute a recovery after its delay |

Design rules that hold throughout the code:

- **The program never transfers shares itself.** A CPI `transfer` of a share mint would call back into `axel_v2` through the hook, which the runtime rejects as reentrancy. The program moves shares only with `mint_to` and `burn`, which do not invoke the hook. Holders, and other programs, transfer through Token-2022.
- **No instruction pays out of a vault to anyone other than the people the money belongs to.** The escrow goes to the operator's and the treasury's canonical accounts on activation, or back to each buyer on refund. The revenue vault pays only a holder's canonical account on claim. Nothing sweeps a vault.
- **Every share account that can move shares has exactly one position.** New share accounts are frozen by default, and the program thaws only an owner's associated token account, together with its `Position`. The hook fails any transfer after which a balance differs from its position.
- **Fees are fixed per project.** `raise_fee_bps` and `revenue_fee_bps` are copied from the config when a project is created, under hard caps in the program.

## Share mint and payment mint

Each project has its own Token-2022 share mint, created by `create_project` at a fresh keypair address.

| Setting | Value | Why |
| :--- | :--- | :--- |
| Decimals | 0 | shares are whole units |
| Mint authority | project PDA | the program mints only in `buy_shares` during the raise, and in `execute_recovery` the same amount it burns, so the supply never grows after the raise |
| Freeze authority | project PDA | the program only thaws, and only an owner's canonical account |
| TransferHook | program `axel_v2`, authority none | nobody can point the hook elsewhere or switch it off; a hook bug is fixed by a program upgrade |
| DefaultAccountState | Frozen | a share account works only after `buy_shares`, `open_position` or `execute_recovery` thawed it |
| PermanentDelegate | project PDA | used only by `execute_recovery`, after a time lock and an owner veto window; no human key holds it |
| MetadataPointer | to the mint itself, authority none | |
| TokenMetadata | name, symbol, uri and up to 8 car attributes; update authority project PDA | the program never updates it after creation |
| TransferFeeConfig | not present | a transfer fee would make balances differ from positions, and its authority could confiscate shares (v1 A5) |

Payment mints (a tenge stablecoin, USDC, or the devnet test token) must be in `Config.allowed_payment_mints` (up to 4). SPL Token mints are accepted. A Token-2022 mint is accepted only with these extensions: MintCloseAuthority, PermanentDelegate, MetadataPointer, TokenMetadata, the group extensions, Pausable, DefaultAccountState set to Initialized, and a TransferHook with no program. Every other extension is rejected, including transfer fees, an active transfer hook, non-transferable, frozen-by-default accounts, interest-bearing and scaled UI amounts, and confidential transfers. The check is an allowlist, so an extension added to Token-2022 later is rejected until reviewed. A permanent delegate, Pausable and a freeze authority on the payment mint let its issuer freeze or seize vault balances; the frontend has to disclose that.

## Accounts and seeds

Seeds are byte strings from `constants.rs` (`CONFIG_SEED` and so on, exported in the IDL). `project` and `owner` sit at fixed offsets so that `getProgramAccounts` memcmp filters work. Rent is the upper estimate `(size + 128) × 6 960` lamports.

| Account | Seeds | Size | Rent (SOL) | memcmp offsets |
| :--- | :--- | ---: | ---: | :--- |
| `Config` | `["config"]` | 358 | 0.00338 | — |
| `Investor` | `["investor", wallet]` | 62 | 0.00132 | `wallet` 8 |
| `Project` | `["project", share_mint]` | 517 | 0.00449 | `share_mint` 8, `state` 232 |
| `Position` | `["position", project, owner]` | 121 | 0.00173 | `project` 8, `owner` 40 |
| `RevenuePeriod` | `["period", project, index as u32 LE]` | 206 | 0.00232 | `project` 8 |
| `RecoveryRequest` | `["recovery", project, from_owner]` | 193 | 0.00223 | `project` 8, `from_owner` 40, `to_owner` 72 |
| Hook validation account | `["extra-account-metas", share_mint]` | 226 | 0.00246 | — |
| Escrow vault (token account) | `["escrow", project]` | token account | | authority = project PDA |
| Revenue vault (token account) | `["revenue", project]` | token account | | authority = project PDA |

The share mint (729 bytes with the seed script's metadata) is a keypair account, not a PDA. Each holder also has a Token-2022 associated token account for the share mint and, for claims, one for the payment mint.

Fields worth knowing:

- `Config`: admin and pending admin (two-step handover), KYC and demo KYC keys, treasury, fees for new projects, minimum raise duration, maximum activation window, allowed payment mints, global pause flag, project count, recovery delay.
- `Investor`: status (`None`, `Active`, `Revoked`, `Frozen`), flags (`DEMO`, `QUALIFIED`, `PROGRAM`), ISO 3166 jurisdiction, expiry, provider (`Manual`, `Sumsub`, `Demo`).
- `Project`: mints, payment token program, operator, oracle, both vaults, state, `ALLOW_DEMO` flag, price per share (immutable), total shares, soft cap, sold, refunded and retired shares, deadlines, the fee snapshot, the accumulator `acc_per_share` (Q64.64), totals of deposits, fees, claims and refunds, period count, telemetry head, count and last date, and the acquisition document hash.
- `Position`: shares (always equal to the owner's share balance), accumulator checkpoint, settled but unclaimed revenue, total claimed, total paid in the raise.
- `RevenuePeriod`: index, declared period dates (YYYYMMDD), gross, fee, net, supply, accumulator after the deposit, report hash, attestor, telemetry head at the deposit, kind (`Regular` or `Final`), actual deposit time.
- `RecoveryRequest`: project, both wallets, shares, reason hash, proposer (gets the rent back), proposal time and `eta`.

## Transfer hook

Token-2022 calls `execute` on every share transfer after it has moved the balances. The hook receives `source, mint, destination, authority, validation account` and six extra accounts that Token-2022 resolves from the validation account:

| Index | Account | Resolution | Writable |
| ---: | :--- | :--- | :---: |
| 5 | config | fixed address | |
| 6 | project | fixed address | |
| 7 | source investor | `["investor", source token account owner]` (`AccountData(0, 32, 32)`) | |
| 8 | destination investor | `["investor", destination token account owner]` | |
| 9 | source position | `["position", project, source owner]` | ✓ |
| 10 | destination position | `["position", project, destination owner]` | ✓ |

Config and project are stored as fixed addresses because Token-2022 re-derives every seeded address on each transfer, at 1 500 compute units per bump attempt. Investors and positions follow the token accounts' owners, not the transfer authority, so a delegate cannot move the shares of an owner who lost KYC.

Checks, in order:

1. Both token accounts belong to Token-2022 and carry the `transferring` flag, which Token-2022 sets only while it invokes the hook. A direct call to `execute` fails with `NotTransferring`.
2. The mint is the project's share mint.
3. The protocol is not paused and the project is Operating.
4. Both owners have an eligible KYC record: Active, not expired, and DEMO only if the project accepts demo investors. Failures are `SourceNotAllowed` or `DestinationNotAllowed`, with the reason in the log.
5. Positions are loaded by hand and matched to the project and owner, because Anchor 0.32 does not reject duplicate mutable accounts. A missing destination position is `RecipientNotOnboarded`.
6. Both positions are settled, the amount moves from one to the other, and the transfer fails with `LedgerMismatch` unless each balance now equals its position.

A transfer costs about 40k compute units when Token-2022's address derivations need no retries, and up to about 66k depending on the keys; the test bounds the key-independent part below 80k. A recipient needs a position first. Its share account does not exist or is still frozen until `open_position`, so Token-2022 rejects the transfer before the hook (`IncorrectProgramId` or `AccountFrozen`). The app should add `open_position` to the same transaction (about 94k compute units together).

## Revenue math

The accumulator `acc` is revenue per share in Q64.64 (`math.rs`):

```
deposit:  fee = floor(gross × revenue_fee_bps / 10 000); net = gross − fee
          acc += floor(net × 2^64 / supply)              supply = sold − refunded − retired
settle:   owed = floor(shares × (acc − checkpoint) / 2^64); accrued += owed; checkpoint = acc
claim:    settle; pay accrued; accrued = 0
recovery: moved = floor(accrued × shares_moved / shares_held)
```

- **No overpayment.** `supply × floor(net × 2^64 / supply) ≤ net × 2^64`, and each holder's share floors again, so the sum of all payouts never exceeds the sum of net deposits. Checkpoints store the exact `acc`, so rounding never accumulates upward.
- **Dust.** Each deposit and each settle loses less than one base unit; the dust stays in the vault. No instruction sweeps it.
- **No overflow.** `shares × Δacc ≤ supply × acc ≤ total_deposited_net × 2^64 < 2^128`, because `total_deposited_net` is a u64 grown with `checked_add`.
- **Raise.** A purchase costs `shares × price` (checked u128 → u64). A refund returns exactly that. Activation splits `gross = outstanding × price` into `floor(gross × raise_fee_bps / 10 000)` for the treasury and everything else in the escrow for the operator, so there is no dust.
- **Sale of the car.** The sale or insurance payout is a `deposit_revenue` of kind `Final` through the same accumulator, before `close_project`. After closing, claims stay open for good.

Invariants checked after every step of the randomized tests (`tests-v2/helpers/invariants.ts`):

- **I1** revenue owed to holders ≤ deposited net − claimed ≤ revenue vault balance;
- **I2** share supply = sold − refunded − retired = sum of positions;
- **I3** every holder's share balance = its position;
- **I4** escrow balance = (sold − refunded) × price while the escrow exists;
- **I5** no position's checkpoint is ahead of `acc`.

## Recovery governance

The share mint has a permanent delegate, the project PDA, so that a holder who lost its key, or its heirs, can get the shares back. Only `execute_recovery` uses it, and only through this process:

1. **Propose.** The admin calls `propose_recovery` with the old wallet, the new wallet, the number of shares and the SHA-256 of the off-chain case file. The new wallet needs an eligible KYC record. The request lives at `["recovery", project, old wallet]`, one per wallet and project, with `eta = now + recovery_delay`. Changing the delay later does not move a pending request. Both wallets are accounts of the transaction, so the proposal shows up in the old wallet's history.
2. **Veto.** Until `eta`, the old wallet can cancel the request. The admin can withdraw it at any time before it runs. Neither pause blocks a cancellation.
3. **Execute.** From `eta`, anyone can call `execute_recovery`. It re-checks the pause, the freeze, the new wallet's KYC, the share count and both ledgers. Then it settles both positions, burns the shares from the old wallet's canonical account, mints the same number to the new wallet's canonical account (thawing it if someone created it frozen), and moves the old wallet's unclaimed revenue pro rata.

Guarantees, each covered by `tests-v2/recovery.test.ts`: the supply never changes; the request cannot be redirected to another wallet or used against a wallet it does not name; the rent goes back to the proposer only; a request runs once; a sanctions-frozen wallet is never touched; and recovery works in every project state, so a lost key cannot strand a refund or the proceeds of the car's sale. The admin cannot burn or move shares through Token-2022 directly, because only the project PDA holds the delegate.

`recovery_delay` must be between 1 hour and 30 days. The 1-hour floor keeps a devnet demo possible. Mainnet needs at least 72 hours, a Squads multisig as admin and a Squads multisig as upgrade authority. A stolen key can veto too: recovery is meant for lost keys and inheritance, not theft.

## Revenue attestation

A revenue deposit needs two signatures: the project's operator, who pays, and the project's oracle, the fleet's reporting system, which attests the report. Both sign the same transaction, so the oracle's signature covers the amount, the period dates, the report hash and the kind.

- A missing oracle signature fails with `AccountNotSigner`, a different co-signer (including the operator signing twice) with `InvalidAttestor`, and a different operator with `Unauthorized`.
- The operator and the oracle must be different keys when the project is created and whenever the roles change (`RoleConflict`).
- `RevenuePeriod` stores the attestor, the report hash (the SHA-256 of the period's published P&L report) and the telemetry chain head at the time of the deposit. The declared dates and the actual deposit time are both on record, so a backfilled period is visible as such.
- Telemetry is a hash chain in the project: `head = sha256(head ‖ date as u32 LE ‖ data_hash)`, where `data_hash` is the SHA-256 of the day's canonical (RFC 8785) JSON report. Dates are real calendar days and strictly increase, so no day can be rewritten or inserted. Anyone with the published reports can recompute the head and compare it with the chain.

In practice the backend builds the deposit, signs it with the oracle key, and the operator's wallet adds its signature.

## IDL and TypeScript client

- `anchor build` writes `target/idl/axel_v2.json` and `target/types/axel_v2.ts`. `npm run export-idl` copies both into `frontend/src/lib/solana/idl-v2/`, so the frontend builds without an Anchor toolchain. CI fails if the committed copy differs from a fresh build.
- `npm run generate` runs `scripts/generate-clients.ts`: Codama reads the IDL, gives every PDA one name (`findInvestorPda`, `findPositionPda`, `findRevenuePeriodPda`, `findRecoveryRequestPda` and so on), links the accounts to their PDAs, and renders a `@solana/kit` client into `sdk/axel-v2/src/generated`. CI fails if the committed client differs from a fresh generation.
- `sdk/axel-v2` is a private package (`@axel/sdk-v2`) with `@solana/kit` 6 as a peer dependency. Async builders such as `getExecuteRecoveryInstructionAsync` fill in every PDA and associated token account from the few accounts a caller knows. `deposit_revenue` needs the `period` account from `findRevenuePeriodPda({ project, index: project.periodCount })`, and a share transfer is a Token-2022 `transfer_checked` with the hook accounts listed in [Transfer hook](#transfer-hook).

## Build, test and deploy

Toolchain: Rust 1.89.0 (`rust-toolchain.toml`), Agave 2.3.13, Anchor CLI 0.32.1, Node 22. The root `Cargo.toml` pins platform-tools v1.52 and builds `axel-v2` with `opt-level = "s"`.

```bash
export PATH="$HOME/.cargo/bin:$HOME/.local/share/solana/install/active_release/bin:$PATH"

anchor build                       # or: anchor build -p axel_v2
anchor idl build -p axel_v2 -o target/idl/axel_v2.json -t target/types/axel_v2.ts   # IDL only
cargo fmt -p axel-v2 --check
cargo clippy -p axel-v2 --all-targets -- -D warnings
cargo test -p axel-v2
npm run test:v2                    # installs tests-v2 dependencies when its lockfile changed
npm run export-idl                 # refresh frontend/src/lib/solana/idl-v2
npm ci && npm run generate         # refresh sdk/axel-v2
npm --prefix sdk/axel-v2 ci && npm --prefix sdk/axel-v2 run typecheck && npm --prefix sdk/axel-v2 test
```

The `programs` job in [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs the same steps and caches the toolchains.

**Size and rent.** The release build is 811 688 bytes. The program data account costs at most `(811 688 + 128) × 6 960 = 5 650 239 360` lamports, about **5.65 SOL**, and about 4.12 SOL at the 5 080 lamports per byte measured on devnet. A deploy also needs a buffer account of the same size for the duration of the deploy; its rent is returned when the deploy finishes. An upgrade to a larger program needs `solana program extend` first.

**Local deploy** (no devnet SOL is needed):

```bash
solana-test-validator --reset                      # separate terminal
solana config set --url localhost
cp ~/.config/axel-demo/axel_v2-keypair.json target/deploy/axel_v2-keypair.json
solana program deploy target/deploy/axel_v2.so --program-id target/deploy/axel_v2-keypair.json
```

Then the deployer, as upgrade authority, calls `initialize_config` with the admin, KYC keys, treasury, fees, windows, payment mints and recovery delay.

**Devnet and mainnet.** Deploy once with the same keypair. On mainnet, before any project is created: hand the upgrade authority to a Squads multisig, set `admin` to a Squads multisig through `propose_admin` and `accept_admin`, keep `demo_kyc_authority` at the default key, and set `recovery_delay` to at least 72 hours.

## Open items

- **Program size.** 811 688 bytes, about 5.65 SOL of rent at the upper rate plus a temporary buffer of the same size. `opt-level = "z"` saves about 6% more at 10–25% more compute.
- **Closing before the Final deposit.** `close_project` does not require a `Final` deposit first. If the admin closes a project before the sale proceeds are deposited, they can no longer be deposited on-chain. The admin cannot take the money, but the payout depends on the operator and the admin acting in order.
- **Stolen keys can veto a recovery.** Tying the veto to active KYC would stop that, but then the admin and the KYC key together could take anyone's shares.
- **Wallets and the hook.** Wallets that do not resolve extra accounts cannot transfer shares; the app has to build transfers with the hook accounts itself, plus `open_position` for a first-time recipient.
- **Telemetry `status` codes** are not interpreted on-chain and must be defined in the published report schema.
- **The oracle pays for 20-entry telemetry batches.** A separate fee payer or a compute budget instruction would push the transaction past 1 232 bytes.
