# AXEL — Платформа токенизации реальных активов

## Что это такое

AXEL — это платформа, которая позволяет токенизировать реальные физические активы (на текущем этапе — автомобили в таксопарке) и привлекать инвестиции через блокчейн Solana. Инвестор покупает токены, каждый из которых представляет долю владения конкретным автомобилем. Автомобиль работает в таксопарке, приносит выручку, и эта выручка распределяется между держателями токенов пропорционально их долям.

Вся критически важная бизнес-логика (покупка токенов, распределение выручки, whitelist) работает **на блокчейне** — то есть записана в смарт-контрактах (в экосистеме Solana они называются **программами**), и её невозможно изменить без обновления программы. Это обеспечивает прозрачность для инвесторов: любой может проверить, сколько токенов выпущено, сколько выручки внесено и кто что получил.

## Архитектура проекта

Проект состоит из четырёх основных частей:

```
┌──────────────────────────────────────────────────────────────────┐
│                         FRONTEND (Next.js)                       │
│   Каталог активов, инвестирование, дашборд, панель админа         │
│   Подключение через Phantom Wallet                                │
└──────────────┬───────────────────────────┬───────────────────────┘
               │ RPC-запросы к блокчейну   │  HTTP (телеметрия)
               ▼                           ▼
┌──────────────────────────┐   ┌───────────────────────────────────┐
│   SOLANA BLOCKCHAIN      │   │         BACKEND (NestJS)          │
│                          │   │                                   │
│  ┌────────────────────┐  │   │  Yandex Fleet API → Телеметрия   │
│  │  Программа AXEL    │  │   │  (пробег, поездки, выручка)       │
│  │  (смарт-контракт)  │  │   │                                   │
│  └────────────────────┘  │   │  Запись хэшей на блокчейн         │
│  ┌────────────────────┐  │   │  (oracle)                         │
│  │  Transfer Hook     │  │   │                                   │
│  │  (проверка KYC)    │  │   └───────────────────────────────────┘
│  └────────────────────┘  │
└──────────────────────────┘
```

### 1. Solana-программы (смарт-контракты)

Это ядро системы. Написаны на Rust с использованием фреймворка **Anchor** (аналог ORM/фреймворка для Solana-программ — генерирует boilerplate, валидацию аккаунтов и сериализацию).

Две программы:
- **axel** — основная бизнес-логика
- **transfer_hook** — дополнительная программа, которая автоматически вызывается при каждой передаче токенов и проверяет, что обе стороны (отправитель и получатель) есть в whitelist

### 2. Frontend (Next.js)

Веб-приложение с интернационализацией (EN / RU / KK). Общается напрямую с блокчейном — без собственного API-сервера для бизнес-логики. Все данные о проектах, токенах, выплатах читаются из блокчейна через RPC.

### 3. Backend (NestJS)

Лёгкий сервис без базы данных. Единственная задача — **телеметрия**: ежедневно забирает данные из Yandex Fleet API (поездки, пробег, выручка автомобиля), хэширует их и записывает хэш на блокчейн. Frontend запрашивает у бэкенда последние данные для отображения виджета телеметрии.

### 4. Solana блокчейн

Распределённая база данных и среда выполнения. Все данные (состояние проекта, записи об инвестициях, периоды выплат, whitelist) хранятся в **аккаунтах** на блокчейне. Каждый аккаунт — это бинарная запись фиксированного формата, привязанная к программе-владельцу.

## Ключевые понятия Solana, используемые в проекте

**Аккаунт (Account)** — базовая единица хранения данных на Solana. Это слот памяти с уникальным адресом (публичным ключом), в котором программа хранит свои данные. Аналог строки в таблице базы данных.

**PDA (Program Derived Address)** — детерминированный адрес аккаунта, вычисляемый из набора "семян" (seeds) и ID программы. Аналог составного первичного ключа. Зная семена, любой клиент может вычислить адрес аккаунта без запроса к сети. Например, аккаунт whitelist для кошелька `ABC...` всегда находится по адресу `PDA(["whitelist", ABC...], program_id)`.

**IDL (Interface Definition Language)** — JSON-схема программы, автоматически генерируемая Anchor. Описывает все инструкции, их параметры и структуры данных. Аналог OpenAPI/Swagger для REST API — используется фронтендом для формирования транзакций.

**Транзакция** — атомарная операция на блокчейне. Содержит одну или несколько инструкций, подписанных кошельком пользователя. Аналог HTTP-запроса к API, но подписанного криптографическим ключом.

**Mint** — аккаунт, описывающий конкретный тип токена (его параметры, общее количество, расширения). В нашем случае каждый автомобиль = один mint = один тип токена.

**Token Extensions (Token-2022)** — расширенная версия токен-программы Solana с дополнительными возможностями (комиссия за переводы, заморозка по умолчанию, метаданные прямо в mint-аккаунте и т.д.).

**ATA (Associated Token Account)** — токеновый кошелёк пользователя для конкретного типа токена. Адрес вычисляется детерминированно из адреса кошелька и mint. У каждого инвестора для каждого проекта автоматически создаётся свой ATA.

## Как работает бизнес-логика

### Жизненный цикл проекта

```
Создание проекта (initialize_project)
        │
        ▼
   ┌─────────┐    whitelist инвесторов
   │  Active  │◄── admin одобряет кошельки
   │         │
   │  Инвесторы покупают токены (buy_tokens)
   │  Admin вносит выручку (deposit_revenue)
   │  Инвесторы забирают долю (claim_revenue)
   │         │
   └────┬────┘
        │ pause_project / resume_project
        ▼
   ┌─────────┐
   │ Paused  │ — покупка и получение выплат приостановлены
   └────┬────┘
        │ close_project
        ▼
   ┌─────────┐
   │ Closed  │ — проект закрыт навсегда (необратимо)
   └─────────┘
```

### Инструкции программы AXEL

Каждая инструкция — это отдельная точка входа в программу (аналог эндпоинта REST API).

#### Административные инструкции

| Инструкция | Описание |
|---|---|
| `initialize_project` | Создаёт новый проект. Генерирует токен (mint) с расширениями Token-2022. Задаёт цену доли, общее количество токенов, oracle для телеметрии. |
| `deposit_revenue` | Вносит выручку за период. Admin переводит SOL в revenue vault (хранилище выручки), создаётся запись `RevenuePeriod` с суммой и снимком количества проданных токенов. |
| `pause_project` / `resume_project` | Приостановка и возобновление проекта. В паузе инвесторы не могут покупать токены и получать выплаты. |
| `close_project` | Необратимое закрытие проекта. |
| `add_to_whitelist` / `remove_from_whitelist` | Управление списком одобренных кошельков. Только одобренные кошельки могут покупать и передавать токены. |
| `update_price` | Обновление цены доли. |
| `revoke_mint_authority` | Отзыв права на выпуск новых токенов (когда все доли проданы). |

#### Инвесторские инструкции

| Инструкция | Описание |
|---|---|
| `buy_tokens` | Покупка токенов. Инвестор переводит SOL администратору, программа минтит (выпускает) токены прямо в ATA инвестора. При первой покупке автоматически создаётся ATA и размораживается (т.к. по умолчанию новые аккаунты заморожены). |
| `claim_revenue` | Получение доли выручки за конкретный период. Формула: `(баланс_токенов / snapshot_проданных) * сумма_за_период`. SOL переводятся из revenue vault инвестору. Создаётся запись `ClaimRecord`, чтобы нельзя было получить дважды. |

#### Oracle-инструкции

| Инструкция | Описание |
|---|---|
| `record_telemetry` | Запись хэша телеметрических данных на блокчейн. Вызывается бэкенд-сервисом от имени oracle-кошелька. Позволяет верифицировать, что данные о работе автомобиля не были подделаны. |

### Структуры данных на блокчейне

Каждая структура хранится в отдельном PDA-аккаунте.

| Структура | Seeds (ключ) | Описание |
|---|---|---|
| `ProjectState` | `["project", mint]` | Основное состояние проекта: admin, mint, цена доли, кол-во проданных токенов, статус, счётчик периодов |
| `RevenuePeriod` | `["revenue_period", mint, period_index]` | Запись о внесённой выручке за период: сумма, snapshot проданных токенов, дата |
| `ClaimRecord` | `["claim", revenue_period_pda, wallet]` | Флаг: получил ли инвестор выплату за конкретный период. Если PDA-аккаунт существует — значит, уже получил |
| `WhitelistEntry` | `["whitelist", wallet]` | Одобрен ли кошелёк для участия (approved: bool) |
| `TelemetryRecord` | `["telemetry", mint, date]` | Хэш телеметрии за конкретный день |

Revenue vault (хранилище выручки) — это PDA `["revenue", mint]`, обычный системный аккаунт, на котором хранятся SOL для выплат инвесторам.

## Token Extensions — расширения токена

При создании проекта (`initialize_project`) mint настраивается с шестью расширениями Token-2022:

| Расширение | Назначение |
|---|---|
| **TransferHook** | При каждом переводе токена автоматически вызывается программа `transfer_hook`, которая проверяет whitelist обеих сторон. Если кто-то не одобрен — перевод отклоняется. |
| **DefaultAccountState (Frozen)** | Новые токеновые аккаунты создаются в замороженном состоянии. Размораживаются только при покупке через `buy_tokens` (после проверки whitelist). |
| **PermanentDelegate** | Администратор имеет постоянное право переводить/сжигать токены из любого аккаунта. Нужно для разрешения споров и compliance. |
| **TransferFeeConfig (1%)** | Комиссия 1% (100 basis points) автоматически удерживается при каждом переводе токенов между кошельками. |
| **MetadataPointer** | Метаданные токена (название, символ, VIN автомобиля, марка, модель, год, оценочная стоимость) хранятся прямо в mint-аккаунте, а не в отдельном аккаунте. |
| **TokenMetadata** | Сами метаданные: имя токена, символ, URI, а также произвольные пары ключ-значение (VIN, марка, модель и т.д.) |

### Transfer Hook — как работает KYC-проверка

Transfer Hook — это отдельная программа, которая вызывается автоматически токен-программой при каждом переводе. Её задача — убедиться, что и отправитель, и получатель токенов находятся в whitelist.

```
Инвестор A → перевод токенов → Инвестор B

Token-2022 программа:
  1. Видит, что у mint включён TransferHook
  2. Находит ExtraAccountMetaList PDA — список доп. аккаунтов
  3. Автоматически добавляет к вызову:
     - WhitelistEntry PDA отправителя
     - WhitelistEntry PDA получателя
  4. Вызывает transfer_hook.execute(amount)

transfer_hook.execute:
  - Читает WhitelistEntry отправителя → approved == true?
  - Читает WhitelistEntry получателя → approved == true?
  - Если обе проверки пройдены → перевод разрешён
  - Если нет → транзакция откатывается
```

## Frontend — веб-приложение

### Технологии
- **Next.js 14** (App Router) — React-фреймворк с серверным рендерингом
- **next-intl** — интернационализация (3 языка: EN, RU, KK)
- **Tailwind CSS** — утилитарный CSS-фреймворк
- **@solana/wallet-adapter** — библиотека для подключения Solana-кошельков (Phantom и др.)

### Страницы

| Маршрут | Описание |
|---|---|
| `/` | Лендинг — описание платформы, кнопка "Explore Assets" |
| `/assets` | Каталог проектов — карточки с фото, ценой токена, прогрессом продаж, статусом |
| `/assets/[id]` | Детальная страница проекта — прогресс сбора, характеристики авто, прогноз доходности, кнопка "Invest Now" |
| `/dashboard` | Портфель инвестора — токены, их стоимость, доступные и полученные выплаты, виджет телеметрии |
| `/payouts` | История выплат — таблица всех периодов с суммами и статусами |
| `/admin` | Панель администратора — метрики проекта, управление whitelist, внесение выручки, пауза/закрытие |

### Как frontend общается с блокчейном

Frontend **не имеет собственного backend-API для бизнес-логики**. Все данные читаются напрямую из блокчейна через RPC-запросы:

```
Frontend                          Solana RPC нода
   │                                     │
   │  getProgramAccounts(axel_program)   │
   │ ──────────────────────────────────► │  ← получить все ProjectState
   │                                     │
   │  getAccount(revenue_period_pda)     │
   │ ──────────────────────────────────► │  ← получить данные о периоде
   │                                     │
   │  sendTransaction(buy_tokens_tx)     │
   │ ──────────────────────────────────► │  ← отправить подписанную транзакцию
   │                                     │
```

Для формирования транзакций используется **IDL** программы — JSON-описание всех инструкций и их параметров. Anchor-клиент на TypeScript автоматически сериализует параметры и подставляет нужные аккаунты.

## Backend — сервис телеметрии

### Технологии
- **NestJS** — Node.js фреймворк
- Без базы данных — in-memory кэш (последние 30 дней)

### Как работает

```
Yandex Fleet API                  Backend                      Solana
      │                              │                            │
      │  ◄── getDailyTelemetry()     │                            │
      │       (CRON, ежедневно)      │                            │
      │                              │                            │
      │  orders, revenue, mileage ──►│                            │
      │                              │                            │
      │                              │  SHA-256 хэш данных        │
      │                              │                            │
      │                              │  record_telemetry(hash) ──►│
      │                              │                            │
      │                              │  Кэш в памяти              │
      │                              │                            │
      │                  Frontend ──►│  GET /telemetry/latest/:id │
      │                              │ ──► JSON с данными          │
```

1. **Cron-задача** (по умолчанию каждый день в 01:00) запрашивает Yandex Fleet API — все заказы за предыдущий день
2. Фильтрует по номеру автомобиля, агрегирует выручку, пробег, количество поездок
3. Вычисляет SHA-256 хэш от канонического JSON-представления данных
4. Если настроен oracle-кошелёк — отправляет транзакцию `record_telemetry` с хэшем на блокчейн
5. Кэширует данные в памяти, отдаёт фронтенду через REST-эндпоинт

### Зачем хэш на блокчейне?

Запись хэша — это **proof of existence**. Любой может взять данные телеметрии, вычислить хэш и сравнить с записью на блокчейне. Если хэши совпадают — данные не были изменены после записи. Сами данные телеметрии хранятся off-chain (в кэше бэкенда), на блокчейне — только 32-байтовый хэш.

## Модель монетизации и финансовые потоки

```
                        SOL
Инвестор ──── buy_tokens ────► Admin кошелёк
  │                              (цена доли * количество)
  │
  │         Программа минтит
  │         токены в ATA
  │         инвестора
  ▼
Держатель                        Admin
токенов ◄── claim_revenue ──── deposit_revenue ──── Выручка от
  │         (доля от периода)   (вносит SOL         Yandex такси
  │                              в revenue vault)
  │
  │ Перевод токенов
  │ (1% комиссия)
  ▼
Другой держатель
(если оба в whitelist)
```

**Формула выплаты за период:**
```
payout = (баланс_токенов_инвестора / snapshot_проданных_токенов) * сумма_за_период
```

Snapshot фиксируется в момент `deposit_revenue`, чтобы предотвратить манипуляции (покупка токенов прямо перед выплатой).

## Безопасность

### На уровне блокчейна
- **Whitelist** — только одобренные кошельки могут покупать и передавать токены
- **Transfer Hook** — каждый перевод проходит проверку whitelist (невозможно обойти)
- **Frozen by default** — новые токеновые аккаунты заморожены, пока программа явно не разморозит при покупке
- **PDA-подпись** — минтинг токенов и переводы из vault возможны только через программу (никто не может вызвать их напрямую)
- **ClaimRecord** — защита от повторного получения выплаты (аккаунт создаётся один раз, второй init вернёт ошибку)
- **Overflow-проверки** — все арифметические операции используют `checked_*` методы

### На уровне frontend
- Валидация Solana-адресов перед отправкой
- Валидация сумм
- Санитизация контента (защита от XSS)
- Все данные читаются из блокчейна — невозможно подделать через изменение фронтенда (транзакция всё равно будет валидирована программой)
